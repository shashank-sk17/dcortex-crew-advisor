hand-written expected values.** Companion machine-readable file:
[`core/tests/fixtures/rule_test_matrix.json`](../core/tests/fixtures/rule_test_matrix.json),
generated by scanning `data/scenarios.json` and `data/questions.json` for every
rule-specific reference (question `rules_ref`, scenario `excluded_candidates` reasons,
`breach_detail` / `illegal_assignment` fields). Regenerate it if the dataset changes —
never hand-edit expected values, always pull from the vendored JSON.

This is scoped to Kashifa's owned modules (`World`, `LEX`, cost model, `JOINT`). It is
**not** a replacement for `evals/harness.py` (Gayathri's end-to-end scorer against all
38 questions + 6 scenarios) — it's the rule-level unit-test spec you write `core/`
tests against *before* the full agent loop exists.

## 3. Gap: RULE-FLT-03 has zero dataset-native test cases

Neither the 38 questions nor the 6 scenarios ever exercise the 100h/28-day rule
directly — every scenario's candidate pool happens to pass it without incident. That's
a real coverage hole, not just noise: RULE-FLT-03 has the same calendar-day-window trap
as RULE-DUTY-02 (Trap 1 in `docs/RULES.md`), and nothing in the dataset forces you to
get it right.

**Synthetic test to add**, built from real `duty_clocks.json` values (not invented):

```
C-2143: flight_hours_28d = 79.24  →  headroom = 100 − 79.24 = 20.76h   (near-boundary, should PASS)
C-1042: flight_hours_28d = 64.27  →  headroom = 100 − 64.27 = 35.73h   (comfortable margin, should PASS)
```

C-2143 is the highest `flight_hours_28d` in the dataset (checked directly against
`duty_clocks.json`), so it's the best available near-boundary case. There is no crew
member who actually breaches RULE-FLT-03 in this dataset — if you want a FAIL case,
construct one synthetically (e.g. fork C-2143's `daily_history` and add a duty day
pushing flight hours over 100) and note in the test that it's synthetic, not
dataset-derived, so nobody mistakes it for an answer-key value later.

## 5. How to use `rule_test_matrix.json`

```jsonc
{
  "rules": {
    "RULE-DUTY-02": {
      "questions": [ /* full question objects incl. expected_answer */ ],
      "scenario_exclusions": [ /* {scenario_id, crew_id, reason} for every FAIL citing this rule */ ],
      "scenario_pass_evidence": [ /* breach_detail / illegal_assignment strings citing this rule */ ]
    },
    ...
  },
  "scenarios_index": [ /* id, difficulty, title, event_type for S1-S6 */ ],
  "held_out_index": [ /* id, title, event_type for H1-H2 — reference only, don't test against */ ]
}
```

Each `scenario_exclusions` entry's `reason` string is the literal answer-key text
(e.g. `"RULE-DUTY-02: would exceed 60h/7d by 1h20m on 2026-09-15 (total 61.33h)"`) —
`docs/RULES.md` asks you to match this phrasing in `RuleVerdict.detail` where it exists,
so these are your exact expected strings, not paraphrases.
