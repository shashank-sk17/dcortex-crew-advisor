Crew Operations Advisor — REST API

Frontend-required contract — the endpoints the Ops Console actually calls, including the advisor stream. An extension of Gayathri's REST API v2; tags mark the delta.

Base URL: /api/v1  ·  Content-Type: application/json  ·  Timestamps: UTC ISO-8601  ·  Money: integer INR  ·  Hours: float 2dp

NEW not in v2   RESHAPE in v2 but the body must change   AS v2 take v2's shape unchanged

Response envelope

Adopt v2's envelope. Reads return { "data": … }; collections add "meta": { "count": N }. The frontend unwraps data in one HTTP interceptor — no per-call change. Every derived response also carries "basis": ["flights.json","rules.json", …] (the files + rule IDs it was computed from) — cheap, and it is the "every number traces to a source" story that is scored.

Standard error contract

{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid request parameters",
    "details": [ { "field": "pairing_id", "issue": "pairing_id is required" } ]
  }
}

HTTP status codes: 200 Success · 400 Bad Request · 404 Not Found · 500 Internal Server Error.

Two decisions the frontend needs settled: (1) are derived fields computed in core/ for v1 — delay_rank, crew-row attention/headroom, the funnel? The board and crew list are designed around them. (2) SSE /ask vs sync /advisory — the streaming reasoning trace is a scored demo beat.

4. Flight List RESHAPE

MethodGETEndpoint/api/v1/flights

Request

GET /api/v1/flights?date=2026-09-15&station=BLR&delay_rank=critical

Request Parameters

Required: date (in the operating week). Optional: station, aircraft, status, delay_rank, sort.

Purpose

The main board. Each row carries the derived disruption signals — the board is "colour-coded by delay rank". Sorted server-side by delay_rank_score.

200 — Success

{
  "data": [
    { "flight_id": "DX412-2026-09-15", "flight_no": "DX412", "date": "2026-09-15",
      "dep_station": "BLR", "arr_station": "DEL",
      "dep_utc": "2026-09-15T06:00:00Z", "arr_utc": "2026-09-15T08:45:00Z",
      "block_hours": 2.75, "aircraft": "VT-DXC", "aircraft_type": "A320", "seats": 162,
      "pairing_id": "P-2291",
      "status": "at_risk",
      "delay_rank": "critical", "delay_rank_score": 83,
      "delay_rank_reasons": ["pairing overnights away from base (day-2 orphan risk)"],
      "slack_minutes": 20, "downstream_count": 4, "crew_fdp_headroom_min": 45,
      "basis": ["flights.json","rosters.json","rules.json"] }
  ],
  "meta": { "count": 1 }
}

delay_rank formula (see the frontend mock derive.ts for the reference implementation): slack_minutes = next-tail-departure − this-arrival; crew_fdp_headroom_min = FDP limit − projected duty for the operating pairing that day.

critical : slack < 30  OR  headroom < 30  OR  pairing overnights away from base  OR  downstream_count ≥ 4
high     : slack < 60  OR  headroom < 60  OR  downstream_count ≥ 2
medium   : slack < 120 OR  downstream_count == 1
low      : otherwise

400 — Bad Request

{ "error": { "code": "INVALID_DATE", "message": "'date' is required and must be within 2026-09-14 … 2026-09-20." } }

500 — Internal Server Error

{ "error": { "code": "INTERNAL_ERROR", "message": "Unable to retrieve flights" } }

Implementation Notes

  • One core, two façades. Every REST endpoint and every agent tool call the same core/ function. The agent's tools are a subset — /pairings/{id}/candidates, /crew/{id}/legality, /flights/{id}/downstream, /rank.
  • Derived vs. raw. Endpoints 4, 6, 8, 9, 12, 15 return computed fields. If core/ cannot deliver delay_rank / crew attention for v1, say so — the board and crew list are designed around them and the frontend needs to know before wiring.
  • Envelope. { "data": … } on reads, + "meta": { "count" } on collections, { "error": { code, message, details? } } on failure. Keep "basis" on derived bodies.
  • SSE. text/event-stream, one JSON data: line per event, each with a type. If the team goes sync /advisory instead, its response must still carry the funnel, excluded and near_misses (endpoint 8's payload) or the auditability UI has nothing to show.
  • Optional, not blocking. GET /aircraft and GET /stations — the frontend derives tails and station codes from /flights for v1; add them if a real fleet/station panel lands.
  • Do not expose DB/vector internals (embeddings, search vectors). Sample values here are illustrative but drawn from the real dataset (C-1042, P-2291, RULE-DUTY-02 = 61.33h); the live API computes from core/.
